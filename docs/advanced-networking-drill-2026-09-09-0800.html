Did You Know That?

BGP Enhanced Route Refresh: SOR/EOR makes soft policy replay auditable

Why hard: Basic Route Refresh requests another advertisement without resetting TCP. Enhanced Route Refresh (RFC 7313) adds Start-of-RIB and End-of-RIB framing, letting the receiver distinguish a path that is merely waiting to be replayed from one that genuinely disappeared.

Mechanism: with ERR negotiated in OPEN, SOR marks affected paths stale, the sender replays Adj-RIB-Out, then EOR closes the transaction; stale paths not refreshed can be removed. This differs from inbound soft reconfiguration, which stores an unfiltered local copy of received routes and re-applies local import policy without asking the peer to replay anything.

Cisco IOS XE: current guidance updated April 21, 2026 states ERR is enabled by default. Optional bgp refresh stalepath-time and bgp refresh max-eor-time timers default to 0/disabled. Stale-path protects a receiver that got SOR without EOR; max-EOR bounds a sender unable to finish replay under continuous churn. Cisco logs stale paths remaining after EOR as a consistency signal.

Arista EOS: RFC 7313 support was introduced in EOS 4.24.2F; neighbor capabilities expose Route Refresh and EOR support. PAN-OS: Soft Reset with Stored Info reprocesses locally stored input, while PAN-OS system logs separately expose routed-BGP-refresh-sent. These are different mechanisms.

MEMORY ANCHOR: stored-info replays your stored input; Route Refresh replays the peer’s current output; ERR brackets the replay so stale state can be proven.
Recall: What starts at SOR? What does EOR prove? Why can stored inbound info still matter?

OSPF LSDB overload protection: self-protection can intentionally drop every adjacency

Why hard: max-lsa can do far more than warn. It counts non-self-generated LSAs and can force the OSPF process into an ignore state, disabling adjacencies and clearing/rebuilding state to protect memory/CPU from an LSA explosion.

Cisco: current IOS XE 17 documentation includes OSPFv2 and OSPFv3 examples. IOS XR documents, once configured, a default warning threshold of 75%, ignore count 5, ignore time 5 minutes, and reset time 10 minutes unless overridden. warning-only keeps the process operating while logging threshold/max events.

Field behavior: a redistribution mistake can make every neighbor disappear while Ethernet and BFD remain healthy. That is not contradictory: the routing process is deliberately refusing OSPF traffic. Stop the leak first, then inspect max-LSA count/threshold, ignore state, and recovery timers.

MEMORY ANCHOR: OSPF may look broken because its LSDB protection is working.

MPLS Implicit Null vs Explicit Null: PHP changes the last-hop packet and QoS evidence

Why hard: label 3 is an instruction in signaling; it never appears in a packet. It tells the penultimate LSR to pop before transmission. IPv4 explicit-null label 0 and IPv6 explicit-null label 2 remain on the wire until egress.

Cisco IOS XE: LDP normally advertises implicit-null for directly connected FECs. mpls ldp explicit-null preserves a final MPLS header so egress can still see TC/QoS information. Cisco notes that when a second inner label remains after PHP, explicit-null might be unnecessary solely for QoS preservation.

Juniper: Junos also defaults to implicit-null and supports explicit-null; Juniper warns that mixed-vendor devices can classify based on different label positions. Newer Junos Evolved platforms offer explicit-null-cos inet|inet6 to classify from MPLS TC instead of payload DSCP.

Arista: current EOS RSVP defaults local termination to implicit-null and supports label local-termination explicit-null. Multi-label termination is platform-sensitive on some R-series systems; Arista also documents explicit-null as useful when payload address family needs to remain inferable from bottom-of-stack label semantics.

MEMORY ANCHOR: implicit null says “pop before sending to me”; explicit null says “send one final label so I still see MPLS context.”

IS-IS Remaining Lifetime + Purge Originator Identification: should this LSP die, and who killed it?

Why hard: a corrupted or maliciously tiny Remaining Lifetime can make an otherwise valid LSP age to zero even while every IS-IS adjacency remains Up. RFC 6232 POI solves the forensic half: identify the origin/source of a purge as it floods.

Cisco IOS XR: current Cisco 8000 minimum-lifetime protection prevents a non-originator from purging an LSP prematurely because of a corrupt low lifetime. Related IOS XR behavior uses 1200 seconds as default maximum LSP lifetime; after Remaining Lifetime reaches zero, Zero Age Lifetime keeps the LSP 60 additional seconds. A received lifetime below 60 seconds can generate a possible-corruption log and the received lifetime is visible in show isis database.

Juniper: POI records the system ID of the purge originator. If a purge arrives without POI, Junos can add its own and upstream-source system IDs so forensic breadcrumbs survive flooding. Juniper explicitly mentions malicious low-lifetime LSPs as a threat.

MEMORY ANCHOR: minimum-lifetime asks “should it be allowed to die?” POI asks “who purged it?”

EVPN Default Gateway extended community: Type-2 can describe a host or a gateway

Why hard: Type-2 MAC/IP routes carry both ordinary endpoints and default-gateway identities. RFC 7432 tags gateway MAC/IP advertisements with the Default Gateway extended community so remote PEs understand the semantic role of the binding.

Standard: a PE may advertise its gateway MAC/IP as Type-2 with Default Gateway EC; the ESI is zero. Remote gateways can recognize packets addressed to a remote/old gateway MAC and route them locally after workload mobility, avoiding unnecessary hairpinning.

Juniper: the Default Gateway EC is type/subtype 0x030d. Default behavior is gateway-MAC advertisement. default-gateway do-not-advertise suppresses it; no-gateway-community advertises gateway/IRB information without the EC. Specific VGA/anycast designs require no-gateway-community and Junos prohibits mixing this behavior with ordinary advertise on peer PEs sharing the same multihomed ES.

Counterintuitive anycast case: if all leaves truly own the same VGA/MAC binding, gateway service exists even when the Default Gateway EC is intentionally omitted. Therefore “no gateway community” is not automatically a fault.

MEMORY ANCHOR: Type-2 carries the binding; the Default Gateway community carries the role.

802.11k + 802.11v: infrastructure narrows the search and suggests, but the client normally decides

Why hard: 11k and 11v are often lumped into “fast roaming.” 11k supplies candidate/radio knowledge; 11v supplies a BSS Transition suggestion. Neither is the 802.11r key/authentication acceleration mechanism.

Cisco Catalyst 9800: IOS XE 26.1 11k assisted roaming creates per-client neighbor lists, optionally dual-band. Current 2026 best-practices recommends 11k and 11v. 11v supports client-solicited, load-balance, and optimized-roaming transition requests. Cisco explicitly says the request is advice unless disassociation-imminent is enabled; even then the AP forces leaving after a timer, not the exact AP the client must select.

Aruba: Client Match uses 11v BSS Transition Requests for capable clients and waits for a response. Non-11v clients can be steered more aggressively by temporarily blocking neighboring association and deauthenticating the client. Aruba New Central exposes dot11v per SSID and documents the default as false in the cited API schema.

Troubleshooting: a perfect neighbor report proves candidate information only. A perfect BSS Transition Request proves suggestion delivery only. Check candidate quality, Query/Request/Response, client capability/policy, actual reassociation, RF, then 11r/security exchange.

MEMORY ANCHOR: 11k = where could I roam; 11v = where should I consider; 11r = how do I authenticate faster after deciding.

Scenario learning

Policy changed but one BGP prefix never returns: verify Route Refresh capability, SOR, replay, EOR, stale timer and consistency logs; if using PAN stored-info, verify local RIB-in recalculation instead.
Every OSPF neighbor drops while interfaces/BFD remain Up: correlate redistribution leak, non-self LSA count, max-lsa threshold/maximum, ignore state and recovery timers.
Explicit-null helps QoS on one router and breaks another: inspect complete stack, TC classification position and multi-label termination hardware.
IS-IS neighbors Up, prefixes disappear: inspect Remaining Lifetime, POI, sequence/checksum and originator refresh history.
VM moves but retains old gateway MAC: inspect Type-2 gateway binding, Default Gateway EC/no-gateway-community policy, VGA/IRB MAC and local FIB.
11k/11v frames look perfect but sticky client stays: check candidate quality, BSS Transition response, client policy, disassociation-imminent, RF and subsequent authentication.

Protocol interactions

  • Route Refresh + policy: policy changes matter only after the relevant Adj-RIB is reprocessed/replayed completely.
  • OSPF max-lsa + redistribution: a leak can trigger self-protection while BFD stays healthy.
  • MPLS explicit-null + QoS: PHP changes which TC field remains at the egress.
  • IS-IS lifetime + flooding: topology can die independently of IIH adjacency.
  • EVPN Type-2 + IRB: route type gives reachability; community gives gateway role.
  • 11k + 11v + 11r: candidate knowledge, steering, and authentication are three stages.
