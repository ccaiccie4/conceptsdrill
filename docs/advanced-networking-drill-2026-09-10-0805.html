Beginner primer

ORF: receiver sends filter intent to the BGP sender. Liberal retention: retain alternate remote labels. IMET: EVPN BUM membership. DIS: IS-IS LAN pseudonode owner. FT: fast security transition between APs. AS Override: outbound ASN rewrite.

Did You Know That?

BGP ORF: receiver policy can filter the sender's Adj-RIB-Out

A local inbound prefix list still makes the receiver accept and process UPDATEs before rejection. ORF moves that filtering boundary upstream: the receiver advertises an ORF capability and sends its desired prefix filter to the peer, which applies that filter while generating outbound UPDATEs. The direction names are easy to invert: send means “I can send you my ORF rules”; receive means “I can accept your ORF and use it on what I advertise back.”

Cisco IOS XE's current prefix-based implementation is per address-family, uses IP prefix lists, is documented for external peerings, and requires capability exchange before ORF announcements can be accepted. IOS XR exposes capability orf prefix send|receive|both|none. XR warns that neighbor-specific ORF receive behavior can reduce update replication efficiency because the resulting Adj-RIB-Out can become unique to that peer.

Operationally, capability negotiation proves only that the peers understand ORF. It does not prove the remote filter is installed or that a refresh has rebuilt Adj-RIB-Out. Verify capability, installed ORF, refresh event, remote advertised-routes, then local received-routes.

MEMORY ANCHOR: inbound policy says “I will discard it”; ORF says “do not send it to me.”
Active recall: If A sends ORF to B, who filters outbound updates? Why can ORF save receiver resources? What does negotiated capability fail to prove?

LDP liberal retention vs ordered/independent distribution

LDP mode names describe different dimensions. Retention asks which remote bindings are stored. Liberal mode retains labels from peers even when they are not the current IGP next hop; conservative mode keeps only useful next-hop bindings. Distribution control asks when an LSR may advertise its own label. Independent control can advertise without first receiving a downstream binding; ordered control waits until the LSR is the egress or has an appropriate downstream mapping. Advertisement mode is yet another axis: Downstream Unsolicited vs Downstream-on-Demand.

Cisco IOS XR states liberal retention is default and supports label-acceptance filtering with label remote accept. Nexus documentation makes the orthogonality explicit: Independent distribution control, Liberal retention and Downstream Unsolicited advertisement are defaults in the cited implementation. Junos' standards matrix supports Ordered control, Liberal retention, and both advertisement modes; it does not support Independent control or Conservative retention.

With liberal retention, a binding table can contain labels from multiple peers for one FEC while the LFIB uses only the current IGP next hop's binding. Stored label ≠ active ECMP.

MEMORY ANCHOR: retention = what remote labels I keep; control = when I advertise mine; advertisement = volunteer vs wait to be asked.
Active recall: Which mode pre-stores alternate bindings? Is Ordered synonymous with Conservative? What control mode does Junos support?

EVPN Type-3 IMET/PMSI: the control plane for BUM membership

Type-2 MAC/IP routes answer “where is this endpoint?” Type-3 IMET answers “which remote PEs/VTEPs participate in this broadcast domain?” The IMET route carries EVI/Ethernet-Tag context, originating PE/VTEP information, RT, and a PMSI Tunnel Attribute describing the inclusive replication model. Ingress replication makes the headend create one unicast copy per remote participant; multicast/P2MP transport can move replication into the core.

Cisco documents IMET per EVI/Ethernet-Tag and explicitly calls out headend-replication scaling as VTEP count rises. Arista EOS 4.36.2F uses Type-3 for dynamic remote VTEP discovery and ingress flood-list population. Junos describes IMET-based ingress replication and notes that IGMP/MLD snooping is not performed in the EVPN core for that model; Junos can instead signal P2MP LSP information through the PMSI attribute.

A fabric can therefore have perfect Type-2 known unicast while DHCP broadcast, ARP/ND flooding or unknown-unicast forwarding fails because Type-3 membership/flood state is incomplete.

MEMORY ANCHOR: Type-2 locates endpoints; Type-3 builds the flood-domain membership.
Active recall: Which route builds the BUM flood list? Why does headend replication scale poorly? Can known unicast work while DHCP flooding fails?

IS-IS DIS/pseudonode: preemptive election can change SPF without adjacency loss

On an IS-IS broadcast LAN, the DIS represents the LAN as a pseudonode so every router need not advertise a full mesh of LAN adjacencies. A DIS is elected separately for each active level and originates the pseudonode LSP. Unlike OSPF DR election, IS-IS DIS election is preemptive: a higher-priority router arriving later can take over. There is no OSPF-like BDR.

Cisco documents the pseudonode as a scalability mechanism. Junos show isis adjacency detail exposes DIS priority. Juniper also documents the DIS's periodic CSNP database-summary duty: default 10 seconds on a LAN when the router is DIS; cited point-to-point behavior uses 5 seconds. A DIS change can therefore regenerate pseudonode LSP state and cause SPF churn even though every physical adjacency stays Up.

MEMORY ANCHOR: OSPF DR is sticky; IS-IS DIS is competitive. DIS owns the LAN graph representation and synchronization duties.
Active recall: What LSP does the DIS originate? Can a better new candidate preempt? What PDU summarizes the LSDB?

802.11r Fast Transition: OTA vs OTDS changes signaling path, not the roam decision

802.11r reduces the security work during a BSS transition by reusing a mobility-domain key hierarchy instead of repeating a full backend authentication. It does not decide when a client should roam. RSSI/SNR, 802.11k neighbor information, 802.11v steering and the client driver still govern that decision.

With FT Over-the-Air, the client sends FT authentication directly to the target AP. With FT Over-the-DS, the client sends FT action traffic through the current AP/distribution system toward the target. Cisco IOS XE 26.1 documents both methods and FT-SAE; the command security ft over-the-ds selects OTDS while the no-form selects OTA. A subtle deployment restriction: Catalyst 9800 Flex Local Authentication in the cited 17.7 guide supports OTA only, not OTDS. Mist documents .11r reducing authentication/association exchanges and avoiding a new RADIUS Access-Request on subsequent FT roams; its Zebra compatibility option enables FT-over-the-DS and should not be enabled gratuitously. Aruba's cited 6.x campus guide documents OTA and a historical OTDS non-support limitation for that release family.

“11r enabled” does not prove a client used FT. Check FT AKM, mobility-domain ID, PMK cache/key context, actual roam method and RADIUS logs.

MEMORY ANCHOR: 11r makes security transition cheaper after the client decides to move. OTA talks to the target directly; OTDS goes through the current AP.
Active recall: Which method talks directly to the target AP? Does 11r force a sticky client to roam? Why can same-SSID APs still fail FT?

PAN-OS AS-path loop controls: First-AS, Allow-AS-In, AS Override and sender-side detection

Enforce First AS validates that the first AS in an incoming eBGP UPDATE matches the configured neighbor AS; current Advanced Routing documentation says it is enabled by default. That is immediate-neighbor integrity, not the ordinary check for the firewall's own AS later in AS_PATH.

Allow AS In is a receiver-side exception: accept routes containing the local AS, optionally limited by occurrence count. AS Override is sender-side rewriting: in same-AS customer-site designs, the intermediate device replaces the remote site's ASN before sending so the receiving site can keep ordinary own-AS rejection intact. Sender Side Loop Detection is another sender-side mechanism: it suppresses advertising a route when the peer's AS is already in AS_PATH. It is an early optimization, not the same test as Enforce First AS.

These knobs can pull in opposite directions. Troubleshoot by identifying exactly whose ASN is being checked, at what position, and on which direction of the session.

MEMORY ANCHOR: First-AS validates neighbor identity; Allow-AS-In relaxes the receiver; AS Override rewrites before receipt; sender-side detection suppresses a known loop early.
Active recall: Which check is enabled by default? Which design keeps receiver own-AS protection intact for same-AS branches? How does sender-side detection differ from First-AS?

Scenario learning

ORF negotiated, full table remains: verify send/receive directions, transferred filter, remote installation, refresh event, advertised-routes and received-routes. Capability alone is not application.
IGP next hop changes: compare IGP RIB, LDP binding database and active LFIB. Under liberal retention the alternate label can already exist but still be inactive until the IGP selects that peer.
Known unicast works, DHCP fails: inspect Type-3 IMET, RT import, PMSI mode, remote VTEP flood list and replication counters before blaming Type-2 MAC learning.
IS-IS SPF churn with no adjacency flap: check per-level DIS priority, new DIS identity, pseudonode LSP sequence and CSNP source. DIS preemption can change graph ownership without dropping neighbors.
11r enabled, full RADIUS exchange still appears: verify client FT AKM, MDID, PMK cache, OTA/OTDS compatibility and actual roam event. Infrastructure support does not force client use.
Same-AS branches reject each other: compare provider AS Override against scoped Allow-AS-In. Do not disable First-AS; it validates a different boundary.

Protocol interactions

  • ORF + Route Refresh: policy transfer and update replay are separate stages.
  • IGP + LDP: IGP chooses the active neighbor; liberal retention decides whether a usable alternate label is already stored.
  • EVPN Type-2 + Type-3: endpoint location and BUM membership are independent route functions.
  • IS-IS DIS + SPF: pseudonode ownership can change without adjacency failure.
  • 11k + 11v + 11r: know target, suggest target, authenticate faster—three separate stages.
  • AS Override + Allow-AS-In: sender rewrite and receiver exception solve similar topology problems with different loop-safety tradeoffs.
