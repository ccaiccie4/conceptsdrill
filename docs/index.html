Today's hard-memory rotation: EVPN Designated Forwarder election beyond the acronym — RFC 8584 FSM, RT-4 algorithm/capability agreement, HRW stability, AC-aware candidate pruning, preference/non-revertive recovery, and redundancy-mode-specific forwarding.

Core reconstruction rule

EVPN DF is distributed agreement followed by a forwarding role. Prove signal → candidates → algorithm → role → traffic class. Local configuration is intent; received RT-4 state and the resulting candidate set are distributed truth.

Why this is easy to forget

A BGP EVPN session can be Established while the Ethernet Segment election is wrong. RFC 8584 requires participating PEs to agree on the DF algorithm and capabilities signaled with Ethernet Segment Route Type 4; disagreement or absent capability signaling can force fallback to the default election. The operator who checks only local HRW configuration can therefore troubleshoot the wrong algorithm.

Implementation details

Cisco IOS XR: current NCS documentation supports modulo and HRW DF algorithms in relevant port-active deployments. Preference-based non-revertive DF behavior was introduced for listed NCS 5500/5700 platforms in Release 24.1.1 to avoid recovery-time service re-carving and a second traffic interruption. Port-active standby can interact with LACP Out-of-Service signaling.

Arista EOS: EVPN DF election uses RT-4 Ethernet Segment routes. In single-active mode the DF has broad forwarding responsibility; in all-active mode DF status chiefly determines whether BUM traffic is emitted toward the CE, preventing duplicate copies. Current EOS documentation shows show bgp evpn instance exposing ESI, redundancy mode, DF election algorithm, elected DF and NDF.

Junos: the documented default DF election hold timer is 3 seconds. Preference election builds candidates using preference, Don't-Preempt state and IP ordering; Junos 24.2 adds non-revertive preference options. Juniper also warns that mismatched highest/least preference interpretation can elect two DFs. QFX5K has a critical granularity caveat: port-based election is supported rather than per-EVI-per-ESI election.

Hard-memory facts

HRW is about stable ownership under membership change, not merely randomness. The consistent-hash-style calculation reduces collateral service re-carving when a candidate that was not responsible for a service disappears. Recovery convergence is separate from failure convergence. A clean failover can still be followed by a lossy revert-to-primary event. DF semantics depend on redundancy mode and traffic class. Never generalize a single-active non-DF rule to all-active known unicast.

Scenarios

BGP up, BUM duplicates: compare received RT-4s, ESI, algorithm/capability signaling, candidate eligibility, per-service DF result, then CE-facing BUM behavior. Failover clean, recovery lossy: inspect revertive preference behavior and whether non-revertive mode is appropriate. Per-VLAN carving design on QFX5K: validate platform election granularity before debugging the algorithm. Local HRW but effective default: find the peer whose RT-4 does not advertise matching capability.

Layered workflow

Physical/CE attachment → LACP/ES state → underlay → BGP EVPN session → received RT-4/ESI → candidate eligibility → algorithm/capability unanimity → per-EVI/per-port DF result → redundancy-mode forwarding rule → FIB/encapsulation → client/application. Each stage proves only itself.
