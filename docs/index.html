1. BFD across Cisco, Palo Alto, and Juniper

Baseline. BFD is a rapid liveness detector. It does not calculate a replacement route. When BFD declares a peer Down, a registered client such as BGP, OSPF, EIGRP, IS-IS, RIP, a static-route process, or pseudowire service reacts. End-to-end recovery still depends on protocol reconvergence plus RIB/FIB/LFIB and hardware programming.

Palo Alto Networks — PAN-OS behavior

PAN-OS supports BFD for BGP IPv4/IPv6, OSPFv2/OSPFv3, RIP, and static routes. BGP can use single-hop or multihop BFD. PAN-OS uses asynchronous BFD and documents important unsupported options: BFD authentication, Demand mode, Echo mode, Poll sequences, congestion control, and micro-BFD for link aggregation are not supported in this implementation.

OSPF session topology is implementation-specific. On a broadcast segment, PAN-OS establishes BFD with the OSPF DR and BDR; on point-to-point it uses the directly connected neighbor; point-to-multipoint can use individual peers. This means BFD-neighbor counts do not necessarily equal OSPF-neighbor counts.

PAN-OS can share a BFD session when multiple client protocols use the same source/destination pair. If those clients reference different BFD profiles, the profile with the lowest Desired Minimum Transmit Interval can determine effective session behavior. An aggressive profile intended for one routing client can therefore affect another client that shares the same BFD session.

Operationally, a failed BFD-protected static route can be removed from routing/forwarding state. For BGP or OSPF, BFD reports failure to the routing process, which then performs protocol-specific convergence. “BFD detected the failure in 300 ms” is not equivalent to “traffic recovered in 300 ms.”

Inline digest of the PAN-OS source

  • Supported clients include BGP, OSPF/OSPFv3, RIP, and static routing.
  • BGP can use single-hop and multihop BFD.
  • Broadcast OSPF uses DR/BDR BFD relationships rather than one BFD relationship per visible OSPF neighbor.
  • Matching source/destination client protocols can share a BFD session.
  • The most aggressive Desired Min Tx profile can control the shared session.
  • Unsupported modes/options must be considered during interoperability design.
  • Palo Alto guidance warns engineers to think carefully about BFD interaction with BGP graceful restart and HA path monitoring because overlapping failure-handling mechanisms can cause unwanted behavior.

Cisco IOS XE / IOS XR behavior

Cisco exposes BFD as both a session and a client-registration relationship. The useful question is not only “Is BFD Up?” but “Which protocol is registered to this BFD peer?” Current IOS XE documentation provides general and client-specific commands such as show bfd interface, show bfd neighbors, show bfd neighbors client bgp ipv4, show bfd neighbors client eigrp, and show bfd neighbors client ospf.

Depending on platform/release, OSPF, OSPFv3, EIGRP, IS-IS, and BGP can register with BFD globally or at interface/address-family scope. Cisco OSPFv3 documentation notes that BFD initiation occurs for neighbors that have reached FULL. EIGRP named mode can attach BFD under the address-family interface.

A common failure is single-hop versus multihop mismatch. Loopback-sourced BGP peering often needs multihop BFD. Basic IP reachability can be perfect while the BFD-protected BGP session remains down because the two ends disagree on the BFD session model.

show bfd interface
show bfd neighbors
show bfd neighbors client bgp ipv4
show bfd neighbors client eigrp
show bfd neighbors client ospf
show ip ospf neighbor
show ip eigrp interfaces detail

Inline digest of Cisco documentation and community evidence

  • Cisco BFD troubleshooting should verify both the BFD session and the registered routing client.
  • OSPFv3 does not need to start BFD before the OSPF adjacency reaches the appropriate operational state.
  • EIGRP and other clients can register BFD at different configuration scopes depending on platform.
  • A Cisco Community XR/XE case demonstrates that loopback-based BGP BFD can fail when one side expects multihop and the other side is configured as single-hop.
  • Another field pattern is BFD-driven IGP instability propagating into BGP because the BGP next hop or recursion depends on the IGP.

Juniper Junos behavior

Junos supports BFD across routing and service applications and documents BFD for pseudowire VCCV plus micro-BFD on supported link-aggregation platforms. The supported RFC subset is not identical to PAN-OS, so feature parity cannot be assumed merely because both products say “BFD supported.” Timer floors, address families, application attachment, distributed/offloaded processing, and graceful-restart interactions must all be checked.

2. BFD does not replace BGP convergence logic

A BGP peer can fail fast because BFD detects loss of liveliness, but traffic recovery still depends on BGP best-path selection, recursive NEXT_HOP reachability, policy, route installation, FIB programming, and potentially PIC or other pre-installed backup mechanisms. This is why a design should measure service restoration, not just BFD detection.

Scenario: BGP selects a path with unreachable NEXT_HOP

The correct design correction is to make the NEXT_HOP reachable through the IGP/static transport design or apply next-hop-self at the correct boundary. BFD cannot fix an unreachable recursive next hop. If BFD is Up but the selected BGP route has an unresolved next hop, the forwarding problem remains.

Inline operational lesson

  • BFD protects peer/path liveness, not route policy correctness.
  • BGP graceful restart can intentionally preserve routes after a session event, while BFD is designed to declare failure quickly; their interaction must be deliberate.
  • BGP PIC can reduce post-failure forwarding disruption by pre-installing backup path state; BFD can supply the trigger but PIC supplies part of the forwarding reaction.
  • Recursive next-hop tracking is equally important: a BGP session can remain Up while the recursive transport path to a NEXT_HOP disappears.

3. EVPN/VXLAN — remote VTEP liveness is only one layer

VXLAN is the tunnel data plane; MP-BGP EVPN distributes control-plane reachability such as MAC/IP information. A ping to the VTEP loopback verifies only the underlay path to that loopback. It does not prove that the correct EVPN route type exists, the VNI is correct, the route target imported the route, the MAC/FDB is programmed, ARP/ND is correct, or tenant forwarding works.

Arista EOS — bfd vtep evpn

EOS exposes bfd vtep evpn interval <ms> min-rx <ms> multiplier <n> under the VXLAN tunnel interface context. Current EOS documentation associates this with BGP PIC Edge for EVPN/VXLAN remote-VTEP reachability. The documented interval/min-rx range is 50–60000 ms and the multiplier range is 3–50. A symmetric 100 ms interval with multiplier 3 provides a nominal 300 ms failure-detection example.

If VTEP BFD is Up but a host is unreachable, investigate EVPN Type-2 reachability, VNI membership, route-target import/export, MAC/IP tables, ARP/ND, IRB/anycast-gateway state, and hardware forwarding. Do not treat “VTEP BFD Up” as “EVPN service healthy.”

interface Vxlan1
   bfd vtep evpn interval 100 min-rx 100 multiplier 3

Inline digest of the Arista implementation

  • The VTEP BFD function is specifically about remote-VTEP reachability for EVPN/VXLAN.
  • Timer ranges and multipliers are explicitly configurable; deployment values should reflect fabric scale and failure objectives.
  • BGP PIC Edge can reduce forwarding disruption when a remote VTEP path fails.
  • VTEP liveness does not validate EVPN route distribution or endpoint programming.

4. Strong RSSI can still produce poor Wi-Fi

RSSI measures received signal strength. SNR compares wanted signal with the noise floor. Channel utilization measures airtime occupancy. Retries reveal delivery difficulty. A client at -58 dBm can still perform badly when the channel is busy, non-Wi-Fi interference is high, retry rate is high, or the roaming/authentication transition is slow.

HPE Aruba Networking — Central, AirMatch/ARM, ClientMatch

Aruba Central exposes RF data beyond RSSI. Current APIs and RF views expose channel utilization components including transmit, receive, and non-Wi-Fi interference, along with noise floor, errors, drops, and retry information. This lets the engineer distinguish “signal strong” from “airtime healthy.”

Aruba roaming views expose source AP, destination AP, roaming type, radio band, RSSI, and roam latency. Aruba guidance highlights elevated roaming latency—roughly above 50 ms in the cited troubleshooting workflow—as something worth investigating for latency-sensitive clients.

ClientMatch monitors client RF conditions and can identify sticky behavior. With 802.11v clients, it can use transition-management mechanisms. For clients without 802.11v support, Aruba documents a more forceful steering sequence that can temporarily discourage association to radios and deauthenticate the client so it reevaluates alternatives. The client still owns the final association decision.

AirMatch/ARM optimize channel and transmit-power choices. Simply increasing AP power can create oversized cells and asymmetric links: the client may hear the AP well while the AP cannot hear the lower-powered client equally well.

Inline digest of Aruba implementation guidance

  • Channel utilization should be decomposed into Tx, Rx, and non-Wi-Fi interference rather than treated as one opaque number.
  • Noise floor and retry behavior explain many “good RSSI, bad experience” incidents.
  • Roaming analysis should include latency, source/destination AP, band, roam type, and client capability.
  • 802.11k helps clients discover candidates; 802.11v can recommend transitions; 802.11r accelerates authentication/key transition.
  • ClientMatch may influence sticky clients, but it cannot make every client behave identically.
  • Excessive AP transmit power can worsen roaming by making cells too large.

Juniper Mist — client-controlled roaming

Mist documentation emphasizes that the client controls the roam decision. RSSI should be read with history and context, not treated as a universal roam threshold. Mist discusses 802.11k/v/r and exposes roaming history so engineers can correlate RSSI, candidate APs, roam events, and client behavior.

A practical lesson is that -70 or -75 dBm does not mean the same thing for every client. The important question is how the client behaves at that signal level given SNR, channel conditions, application sensitivity, and available neighbor APs.

5. Pseudowire BFD over VCCV checks the service path

PE loopback reachability does not prove pseudowire forwarding. VCCV provides a pseudowire OAM channel; BFD can run in that context to test service-path liveliness.

Juniper Junos VCCV implementation

Junos documents BFD for VCCV with LDP-signaled Layer 2 circuits, BGP Layer 2 VPNs, and VPLS services. The current distributed implementation can move periodic BFD processing away from the Routing Engine to packet-forwarding resources, increasing scale and reducing control-plane load. Juniper documentation also lists implementation prerequisites such as MPLS family configuration on loopback and control-word requirements on some ACX pseudowire combinations.

Useful operational commands include show l2circuit connections to validate the service/signaling state and show bfd session to validate BFD. A healthy IGP plus reachable PE loopbacks does not prove the VC label, control word, VCCV capability negotiation, or pseudowire BFD state is correct.

Inline digest of Juniper VCCV guidance

  • Use VCCV/BFD when you need pseudowire-specific liveliness rather than only IP reachability.
  • Distributed BFD improves scale and reduces Routing Engine burden.
  • Platform prerequisites such as loopback MPLS-family or control-word requirements matter.
  • Troubleshoot service signaling and BFD state separately.

6. Cross-vendor troubleshooting workflow

  1. Physical / Radio: carrier, optics, errors, RSSI, SNR, noise, retries, channel utilization.
  2. Layer 2: VLAN/tagging, STP/MST state, LAG/LACP, MAC learning, MTU.
  3. Layer 3: addressing, ARP/ND, connected/recursive next-hop reachability.
  4. IGP: adjacency state, metrics, LSDB/topology, SPF results.
  5. BFD: session type, negotiated interval, multiplier, client registration, drops.
  6. BGP/MPLS/Overlay: session, route type, policy, NEXT_HOP, labels, VNI, RT import/export.
  7. Forwarding plane: RIB versus FIB/LFIB, MAC/FDB, hardware programming.
  8. Application/client: DNS, authentication, roaming, application retry/timeout behavior.

Rule of thumb

A healthy lower-layer state narrows the fault domain; it does not automatically prove every higher layer. BFD Up does not prove BGP policy. VTEP ping does not prove EVPN. Strong RSSI does not prove good Wi-Fi. PE loopback reachability does not prove a pseudowire.
