Today's hard-memory rotation: OSPFv3 multi-address-family state isolation: RFC 5838 Instance-ID AF demultiplexing, IPv4 AF over IPv6 link-local control carriage, Junos realm-scoped neighbor/LSDB evidence, AOS-CX AF/API behavior, and LSDB → RIB → FIB proof boundaries.

Core reconstruction rule

Payload AF is not protocol carriage. OSPFv3 can advertise IPv4 reachability while its neighbor/control traffic still depends on IPv6 link-local state. Then prove each downstream stage separately: link-local/Instance ID → AF neighbor → AF LSDB → SPF/RIB → FIB → application.

Why engineers forget this

IPv4 ping can succeed on a link while the OSPFv3 IPv4-AF adjacency is broken, because that ping exercises IPv4 data-plane reachability while OSPFv3 control exchange uses IPv6 link-local. A Full neighbor is also not a forwarding certificate: it proves the AF-specific neighbor state machine completed, not that a particular prefix exists in the LSDB, wins SPF, survives route preference or policy, resolves recursively, or reaches hardware forwarding.

Implementation details

AOS-CX 10.15: documented OSPFv3 Instance-ID ranges are 0–31 for IPv6 unicast and 64–95 for IPv4 unicast. If endpoints use Instance IDs mapped to different AF contexts, syntactically valid OSPFv3 packets can arrive without creating the intended AF adjacency. AOS-CX REST v10.18 exposes /system/vrfs/{VRF.name}/ospfv3_af_routers; that object proves configured intent, not runtime neighbor, LSDB, RIB, or FIB state.

Junos: non-default OSPFv3 AFs are mapped to realms with separate neighbor and LSDB state. For IPv4 unicast, evidence should be scoped with commands such as show ospf3 neighbor realm ipv4-unicast, show ospf3 interface realm ipv4-unicast, and show ospf3 database realm ipv4-unicast. A healthy default IPv6-unicast realm does not prove the IPv4-unicast realm is healthy. Junos also documents LDP synchronization with OSPFv3 in IPv4 realms, an example of why an OSPFv2→OSPFv3 migration requires an interaction audit rather than assuming feature equivalence.

Cisco IOS/IOS XE: OSPFv3 address families can support IPv4 and IPv6 unicast, but IPv6 must be enabled on an interface participating in the IPv4 AF. That implementation detail is the practical expression of the same architectural rule: advertised AF and OSPFv3 packet carriage are distinct.

Scenario drill

IPv4 ping works, IPv4-AF neighbor is down: verify IPv6 link-local readiness first, then capture OSPFv3 Hellos, compare Instance ID/AF context, verify AF interface participation, and only then inspect neighbor state. Do not start at the global IPv4 RIB because the RIB is downstream of a neighbor that never formed.

Default OSPFv3 looks healthy but IPv4 routes vanished: on Junos, scope neighbor and LSDB checks to realm ipv4-unicast. Generic OSPFv3 health is incomplete evidence.

Neighbor Full and LSDB correct, traffic still blackholes: stop clearing the neighbor. Compare SPF/RIB selection, competing route preference/policy, recursive next-hop resolution, and finally the FIB. The first broken downstream boundary is the useful one.
