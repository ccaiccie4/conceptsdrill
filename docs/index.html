BGP Add-Path: path IDs prevent implicit withdrawal, not best-path mistakes

Ordinary BGP treats a new advertisement for the same NLRI from one peer as replacing the previous path. RFC 7911 adds a Path Identifier so several paths can coexist. The Path ID is scoped to the peering session; it does not alter LOCAL_PREF, AS_PATH, MED, NEXT_HOP recursion, or guarantee RIB/FIB installation.

Cisco IOS XE / IOS XR. IOS XE separates capability negotiation, path selection, and neighbor advertisement. Cisco explicitly warns that the advertised set must be a subset of the selected candidate set. IOS XR can select backup, group-best, multipath, best, or all paths. Current NCS 5500 documentation keeps a default advertisement limit of 32 and on supported 24.2.1+ systems can raise it to 96.

Juniper. Junos requires compatible send/receive capability on both sides. The cited implementation supports receive for iBGP and eBGP, while send is iBGP-only in that feature context. Newer MX releases support up to 64 paths, with platform/routing-instance restrictions.

Troubleshooting: capability → candidate selection → advertised subset → received Path IDs → recursive next hops → best/multipath/backup → RIB/FIB. A second BGP path is not proof of preinstalled data-plane protection.

MEMORY ANCHOR: Add-Path changes identity on the wire; it creates diversity, not forwarding guarantees.
Active recall: What must both peers negotiate? Why can a received Add-Path be absent from FIB? What happens if Cisco asks a neighbor to advertise paths that were never selected?

OSPF Graceful Restart: helper mode is conditional topology preservation

Graceful Restart is safe only while helpers believe the topology has not materially changed. A helper keeps advertising the restarting router as though it remained present. Strict LSA checking is the guardrail that ends that preserved state when reality changes.

Cisco IOS XE. In the referenced NSF/OSPF implementation helper mode is enabled by default while strict LSA checking is disabled by default. nsf ietf helper strict-lsa-checking terminates assistance when a changed LSA would need to be flooded to the restarting router.

PAN-OS. Current logical-router OSPF help exposes Graceful Restart, Helper Mode, and Strict LSA Checking separately; all are enabled by default. Grace Period defaults to 120 seconds and Max Neighbor Restart Time to 140 seconds, each configurable 5–1800 seconds for OSPFv2. PAN-OS HA also exposes a Graceful Restart Hello Delay and recommends a dead timer at least four times that delay.

Junos. Local graceful restart is disabled by default, yet helper mode is enabled by default. OSPFv2 supports RFC 3623 standard and restart-signaling helper modes; restart-signaling helper is not supported for OSPFv3. Strict LSA checking is enabled by default. restart-duration defaults to 180 seconds; notify-duration defaults to 30 seconds.

Arista EOS. show ip ospf exposes graceful-restart state, timer and helper status, allowing an operator to correlate which neighbor is preserving state.

MEMORY ANCHOR: A helper temporarily lies for the restarting router; strict checking ends the lie when topology truth changes.
Active recall: Which defaults differ between Cisco and PAN/Junos? Why can helper mode be enabled while local GR is disabled?

EVPN MAC mobility: sequence numbers order moves; duplicate detection judges trust

A new MAC location can be a legitimate host move, a virtual-MAC failover, or a Layer-2 loop. The MAC Mobility sequence number selects the newer advertisement; duplicate-MAC detection judges whether moves are happening too frequently to trust.

Junos. Mobility sequence numbers are enabled automatically. Duplicate detection defaults to a 180-second window and threshold 5; after threshold, updates are suppressed. Optional auto-recovery should be longer than the detection window. show evpn database exposes State, Mobility history and advertisement status; clear evpn duplicate-mac-suppression clears suppression. Exclusion lists protect known legitimate movers; MAC-prefix exclusion support was added in 25.2R1.

Cisco IOS XR. Current NCS 540 documentation adds permanent freeze after repeated duplicate detect/recover cycles; three recovery events within a 24-hour window can freeze a MAC/IP. retry-count infinity prevents permanent freeze and allows repeated recovery.

Troubleshooting: MAC identity → local/remote source → sequence/history → threshold/window → suppression/freeze → actual HA event or loop. Higher sequence means newer, not healthy.

MEMORY ANCHOR: Sequence answers “which location is newer?” Duplicate detection asks “is it moving too often to trust?”
Active recall: What are Junos's default window and threshold? Why can an increasing sequence still indicate a loop?

IS-IS overload bit: remove transit responsibility without disappearing

Overload is not shutdown. The router remains in IS-IS and its own prefixes remain reachable, while other routers avoid it as normal transit. This is valuable after reboot because IS-IS can return before iBGP and service routes are ready.

Cisco. Cisco describes overload as protecting the network from a node that cannot safely forward transit, including the startup period where IS-IS converges faster than iBGP.

Junos. overload timeout range is 60–1800 seconds; default 0 means no timeout. advertise-high-metrics instead advertises maximum metrics (63 narrow / 16,777,214 wide), keeping the node available as last-resort transit. An L1/L2 router in overload normally stops route leaking and clears its attached bit. Dynamic overload can be triggered by resource limits; auto-recovery introduced in 23.1 can clear it when resources recover.

Arista EOS. IS-IS graceful restart t2 bounds LSDB synchronization while SPF is deferred; current docs show a 30-second default and 5–300-second range. restart-hold-time is used for planned restart adjacency preservation. GR preserves continuity; overload controls transit readiness.

MEMORY ANCHOR: Overload says “reach me, not through me.” High-metric says “through me only if you must.”
Active recall: Why can adjacency be Up while transit is intentionally avoided? What happens to Junos attached-bit behavior in overload?

MPLS VPN Site-of-Origin: RD is uniqueness, RT is membership, SoO is provenance

RD, RT and SoO appear in BGP/MPLS VPN workflows but solve different problems. RD makes overlapping customer prefixes unique in VPN NLRI. RT controls VRF import/export. SoO records the customer site that originated a route so the route can be prevented from returning to that same multihomed site.

Cisco. IOS XE EIGRP MPLS VPN PE-CE documentation requires a unique SoO per site and the same SoO on all PE/CE attachments serving that site. The PE can filter a VPN route whose SoO identifies the site it is about to advertise into. Cisco calls out a partitioned-site/backdoor restriction: SoO can also prevent that backdoor from acting as an alternate path to prefixes originated in another partition of the same site.

Juniper. Juniper uses SoO in another modern context—automatic BGP label aggregation on selected PTX/Junos Evolved platforms—illustrating that the extended community must be interpreted by the feature consuming it, not by name alone.

Troubleshooting: RD → RT import/export → SoO → PE-CE protocol/redistribution → backdoor links → FIB. Correct RT means the VRF wants the route; it does not mean the route is safe to send back to the originating site.

MEMORY ANCHOR: RD = uniqueness; RT = membership; SoO = provenance.
Active recall: Which attribute prevents return to source site? Why can the right RT still allow a loop? Why does changing RD not solve provenance?

Scenario learning

Add-Path: two paths arrive but failover still reconverges. Verify capability → selection → advertisement → received Path IDs → recursion → RIB/FIB backup state.
OSPF GR: one helper aborts on topology change while another remains helper. Compare strict-LSA defaults/configuration before blaming the restarting router.
EVPN: a virtual MAC triggers suppression during HA. Prove legitimate movement before using a narrowly scoped exclusion; never globally disable loop protection first.
IS-IS: router is reachable but avoided for transit after maintenance. Inspect overload/high-metric/attached state and iBGP readiness.
MPLS VPN: correct RT imports a route that boomerangs into its source site. Inspect SoO and PE-CE policy.

Protocol interactions

  • Add-Path + RR + PIC: alternate control paths matter only if later stages preserve usable backups.
  • OSPF GR + BFD: fast fault detection can conflict with preserving a restarting neighbor.
  • EVPN mobility + HA: legitimate virtual-MAC movement can resemble a loop.
  • IS-IS + iBGP: overload bridges the convergence-speed mismatch after reboot.
  • RT + SoO: RT admits routes; SoO can stop return-to-site loops.
