Beginner primer — terms needed for today's hard facts

Hot-potato routing: prefer the nearest external exit once higher-priority BGP attributes are equal. ORR root: logical IGP location whose viewpoint a route reflector uses when comparing interior cost to BGP next hops. Route-flap dampening: penalty/merit system that suppresses repeatedly unstable BGP paths. MAC-IP binding: mapping used by an EVPN leaf to answer ARP or NDP locally. BSS color: 1–63 identifier carried in Wi-Fi 6 HE frames so a station can distinguish its BSS from overlapping BSSs. OBSS-PD: packet-detect threshold applied to inter-BSS Wi-Fi 6 frames to create spatial-reuse opportunities. Sham link: logical OSPF intra-area point-to-point link between PE VRFs across the MPLS VPN backbone.

1. BGP ORR changes the IGP viewpoint used during best-path comparison

Why this is easy to forget. A traditional route reflector chooses its own BGP best path and reflects that result. If the RR is topologically remote from its clients, its IGP cost to two otherwise-equal exits can be the opposite of a client's cost. The RR session can be completely healthy, ORIGINATOR_ID/CLUSTER_LIST can be correct, and yet every client can still receive a suboptimal hot-potato exit. ORR fixes the viewpoint used for the interior-cost comparison; it does not make every BGP policy attribute client-specific.

Standards baseline. RFC 9107 lets the RR run route selection from a configured IGP location representing one client, a client group, or another logical root. The RFC explicitly notes that higher-priority BGP policy steps still apply before IGP-cost tie-breaking. It also requires the RR infrastructure to have all eligible paths available; between multiple RRs, Add-Path may be necessary so one RR does not hide a path another RR needs for client-specific selection.

Cisco IOS XR. Current Cisco 8000 documentation describes ORR as reverse-SPF calculations from each client or cluster perspective. Only IGP-learned routes are accepted as rSPF inputs; BGP-LU-learned resolution is out of scope, and multiple IGP topologies are not supported. Cisco warns that ORR increases BGP/RIB memory and convergence work. A platform can support up to 256 ORR groups, but Cisco recommends substantially lower operational scale—no more than 32 groups with about 60 clients per group in the cited classical RR guidance. Older Cisco operational documentation exposes the ORRSPF component, which maintains link-state data, per-policy reverse-SPF trees, and special RIB views. Cisco can use a primary, secondary and tertiary root for an ORR client group.

Juniper Junos. Junos enables ORR with optimal-route-reflection under the BGP group and uses igp-primary with optional igp-backup. The easy-to-miss restriction is route resolution: Junos ORR requires the BGP protocol next hop to resolve through an IGP. In ordinary L3VPN/L2VPN/VPLS/MVPN/EVPN deployments, next hops commonly resolve through RSVP or LDP in inet.3; ORR therefore does not work by default for that resolution path. Juniper documents alternatives such as using inet.0 for resolution or leaking IGP routes into inet.3 so the primary resolving route is IGP-derived.

Arista EOS. Arista's ORR feature addresses the same RR-location problem: the reflector chooses a path using the client's IGP perspective rather than its own. Current TOI indexing shows ORR across modern EOS releases and EVPN use cases. The operational lesson is not to translate Cisco's ORRSPF internals or Junos igp-primary syntax literally; validate EOS release-specific configuration and verify which client/root perspective is active.

Field consequence. If clients in two PoPs should hot-potato toward different exits but both receive the exit nearest a centralized vRR, changing LOCAL_PREF is usually the wrong first correction because it globally changes a higher-priority BGP attribute. Verify that candidate paths are present at the RR, that ORR is enabled for the correct address family/client group, that the root is reachable in the link-state database, and that next-hop resolution is eligible for ORR.

MEMORY ANCHOR: ORR does not change “which BGP rules exist”; it changes “whose IGP map is consulted when BGP reaches the interior-cost comparison.”

2. BGP dampening is a decaying memory of instability—and vendor defaults are not equivalent

Why this is easy to forget. Engineers remember “flaps add penalty” but often forget three different thresholds: suppress, reuse, and the maximum suppression cap. Worse, vendors do not always start with the same penalty model or numeric defaults. A route can be present in Adj-RIB-In yet deliberately excluded from use/export because its accumulated instability history has not decayed far enough.

Standards baseline. RFC 2439 describes a penalty that increases when a route is unstable and decays exponentially over a half-life. Suppression begins above a cutoff; reuse occurs after the penalty falls below a lower threshold. Damping was designed to protect the Internet from churn, but overly aggressive settings can delay legitimate recovery, so deployment policy matters as much as syntax.

Cisco IOS XR. Current Cisco 8000 documentation keeps route dampening disabled by default. The cited defaults are half-life 15 minutes, reuse 750, suppress 2000, and maximum suppression four times the half-life (60 minutes with defaults). Cisco's 2026 guide highlights an easy-to-miss exception: a BGP peer reset does not itself incur route dampening penalty even though routes are withdrawn because of the reset. Numeric parameters can be set directly under the address family or derived through a route policy.

Juniper Junos. Junos route damping is also disabled by default. Its current default half-life is 15 minutes and reuse is 750, but the default suppress threshold is 3000—not Cisco's 2000—while max suppression is 60 minutes. Junos uses a figure-of-merit model and can increase merit for withdrawal/readvertisement or path-attribute change. When suppressed, a route is not installed into the forwarding table and is not exported. Junos also enforces configuration sanity: half-life must be lower than max-suppress. This is separate from Junos BFD-session damping and interface damping, which use different units/defaults and protect different notification boundaries.

Palo Alto PAN-OS. PAN-OS makes the migration boundary itself a troubleshooting fact. The legacy virtual-router engine uses a different dampening model: Cutoff default 1.25, Reuse default 5, Max Hold 900 seconds, and separate reachable/unreachable decay half-lives of 300 seconds. Advanced Routing uses conventional values closer to IOS XR/Junos: Suppress Limit 2000, Reuse Limit 750, Half Life 15 minutes, Maximum Suppress 60 minutes. Palo Alto explicitly documents that legacy profiles are incompatible with Advanced Routing profiles; migration recreates them with defaults and does not link them to peer groups automatically. A historical PAN-OS 11.2.0 issue is even more subtle: with Advanced Routing enabled, a dampening profile could remain configured yet have no effect on peers/peer groups; Palo Alto states this issue was resolved in 11.2.1. Configuration presence therefore did not prove feature enforcement in that release.

Operational consequence. “Route is absent from FIB but BGP session is Established” can be deliberate damping rather than next-hop failure or policy reject. Inspect penalty/merit, suppress state, reuse timer, and whether the profile is actually attached/enforced on the software release. Do not compare a PAN legacy Cutoff of 1.25 with an Advanced Routing suppress value of 2000 as if they are the same unit system.

MEMORY ANCHOR: Dampening has two thresholds and one ceiling: cross suppress to disappear, decay below reuse to return, never stay suppressed beyond max-suppress.

3. EVPN ARP/NDP suppression depends on trustworthy MAC-IP binding state

Why this is easy to forget. ARP suppression is not simply “block broadcasts.” The leaf first needs a trustworthy IP-to-MAC binding learned locally or through EVPN Type-2 MAC/IP advertisement. If it knows the binding, it can answer locally. If it does not, a correct implementation may still flood the request to discover a silent host. That fallback is part of healthy behavior, not proof suppression is broken.

Cisco NX-OS. Current Nexus 9000 10.6 guidance says ARP suppression for a VNI is supported when the VTEP hosts the distributed first-hop/anycast gateway for that VNI, with the SVI and anycast gateway properly configured. The suppression setting must match across the fabric for a VNID; inconsistent VTEP configuration is unsupported. Platform support is release-specific—for example, 10.5(2)F added support for Nexus 9500 with the N9K-X9736C-FX3 line card and 10.6(1)F added Nexus 9336C-SE1 support. Cisco's suppression model learns remote host MAC/IP state through EVPN and answers ARP locally; cache miss can still flood to discover silent endpoints.

Arista EOS. The EOS manual explains that Type-2 can optionally carry both MAC and IP binding and that local VTEPs can learn the binding through ARP snooping or DHCP. An important lifetime nuance is that the MAC+IP route can be withdrawn/cleared independently while a MAC-only Type-2 remains. Arista explicitly recommends MAC timeout greater than ARP timeout; otherwise an engineer can wrongly assume the endpoint disappeared because the IP binding aged while Layer-2 reachability remained. Recent Arista TOIs also extend proxy/suppression knowledge for centralized-gateway topologies by advertising SVI virtual and primary gateway addresses in Type-2 routes, reducing gateway ARP flooding.

Juniper Junos. Junos enables proxy ARP/NDP, suppression, and MAC-IP snooping by default in EVPN-MPLS and EVPN-VXLAN bridge domains/VLANs. The binding database can be limited globally or per routing instance/bridge domain/VLAN/interface, and once a configured limit is hit new MAC-IP entries are not added. Starting with 19.1R1, no-arp-suppression became hidden in the CLI; newer documentation again describes the behavior directly. Disabling suppression does not necessarily disable learning: Junos can continue to learn MAC-IP state unless no-mac-ip-learning is also configured. In 26.1R1, no-mac-ip-learning is documented as unhidden; remote EVPN MAC-IP bindings are still accepted even when local data-plane MAC-IP learning is disabled.

Failure boundary. A stale proxy binding can make suppression harmful: the leaf confidently answers ARP with an outdated MAC. Conversely, an empty binding database causes flooding and looks like “suppression not working” even though the system is correctly falling back. Check EVPN Type-2 MAC/IP, local snooping, binding age/limit, duplicate-MAC/mobility history, anycast-gateway state, and only then the ARP flood behavior.

MEMORY ANCHOR: Suppression is a database feature before it is a flooding feature. No correct binding → no safe proxy answer.

4. Wi-Fi 6 BSS coloring only creates a reuse opportunity; OBSS-PD decides when to exploit it

Why this is easy to forget. A different BSS color does not mean “ignore the other AP.” It means the receiver can classify a valid HE transmission as inter-BSS rather than intra-BSS. Spatial reuse is then possible only if the other transmission is weak enough relative to the OBSS-PD threshold and transmit-power constraints. Same-channel RF still obeys interference physics.

Protocol mechanics. Wi-Fi 6 BSS color is a 6-bit field; operational color values are 1–63. Legacy carrier sensing tends to defer for any decodable Wi-Fi frame around the traditional -82 dBm threshold. With a different-color inter-BSS frame, OBSS-PD can use a less-sensitive/higher threshold so a device may transmit concurrently rather than defer. That increases airtime reuse but also raises collision/interference risk, so the standard couples aggressive reuse with transmit-power behavior.

Cisco Catalyst 9800. Cisco IOS XE 26.1 documents band-level BSS-color enablement using ap dot11 {24ghz | 5ghz | 6ghz} dot11ax bss-color. Cisco describes colors 1–63 and OBSS-PD as a threshold higher than the legacy -82 dBm for inter-BSS packets. Hardware caveats matter: older Cisco documentation notes that Catalyst 9120AX supports BSS coloring but does not support OBSS-PD, so “BSS color capable” did not always imply “spatial-reuse threshold capable.” Verification on supported releases exposes HE capability, BSS Color Capable, configuration mode, and current color in per-AP radio output.

HPE Aruba Networking. ArubaOS radio profiles expose bss-color with range 0–63, where 0 is auto and default 0. Aruba's 530 and 550 Series can detect a same-color collision from another BSS on the same channel and automatically change color. bss-color-switch-count controls how many color-switch announcements are sent in beacons before the change; range 0–100, default 10. This is a subtle state transition: changing color immediately without announcement would confuse associated clients that still expect the old color.

Juniper Mist. Mist's Wi-Fi 6 guidance teaches BSS coloring as a dense-network efficiency feature alongside OFDMA, uplink MU-MIMO, 1024-QAM and Target Wake Time. Mist emphasizes that BSS color lets APs/clients distinguish overlapping BSS transmissions and improve efficiency; the operational lesson is to correlate this capability with channel utilization, retries and RF conditions rather than assume enabling Wi-Fi 6 guarantees spatial reuse.

Failure boundary. Two neighboring same-channel APs accidentally share a color. This does not change their BSSID, but it removes the easy intra/inter-BSS distinction for HE receivers. Check current color and collision/change behavior before changing channels or power. If colors differ but utilization remains high, inspect OBSS signal levels and client capability; the inter-BSS frames may simply be too strong to transmit over safely.

MEMORY ANCHOR: Color classifies the transmitter; OBSS-PD decides whether the channel can be reused.

5. OSPF sham links exist because route-type preference can beat your MPLS-path metric

Why this is easy to forget. If two CE sites are in the same OSPF area and also have a backdoor intra-area link, the provider VPN route normally appears to the CE as interarea. OSPF route-type preference selects intra-area before interarea regardless of a seemingly attractive numeric cost. Simply lowering the PE redistribution metric cannot make an interarea VPN path beat an intra-area backdoor. A sham link changes the route type presented by the VPN path: the PE-to-PE logical relationship becomes an OSPF intra-area point-to-point link.

RFC 4577 mechanics. Sham links are optional and manually configured between VRFs. Each endpoint is a 32-bit address in the customer's VPN address space. The endpoint /32 must be distributed by BGP as VPN reachability and must not be advertised by OSPF itself; if the remote endpoint is not installed in the VRF, the sham link is down. OSPF packets cross the VPN backbone between endpoint addresses and are treated as arriving on the sham link only when the MPLS delivery/source/destination conditions match. The sham link is advertised as a Type-1 link and should behave like an OSPF demand circuit. RFC defaults are Hello 10 seconds and Dead 40 seconds.

Loop prevention. RFC 4577's DN bit is separate from the sham-link cost decision. A PE sets DN on LSAs sent toward a CE and ignores LSAs received back from a CE with DN already set, preventing a route exported through the VPN from looping back into the VPN. Type-5 backward compatibility can also use a VPN route tag. The endpoint route itself has a special rule: because BGP reachability is required to keep the sham link up, advertising that endpoint into OSPF would create circular dependency.

Cisco IOS XE. Cisco's 2026 sham-link guide states the feature is required when same-area sites share an OSPF backdoor and the MPLS VPN should be primary. The sham-link creates an OSPF adjacency and database exchange across the MPLS VPN so the provider path becomes intra-area. The configured sham-link cost then competes fairly with the real backdoor's intra-area cost.

Juniper Junos. Junos supports sham links for OSPFv2 routing instances and describes the sham link as a hidden route from 9.6 onward. A BGP route is not exported to OSPFv2 when a corresponding sham link exists. Starting in 16.1, sham links are also supported in default instances; if no metric is configured, Junos can derive sham-link cost from the BGP AIGP metric, otherwise it defaults to 1 when AIGP is absent. Junos endpoint reachability must be propagated by BGP. Junos also exposes domain ID and VPN route tag controls, reinforcing that sham-link path preference and PE/CE loop prevention are separate mechanisms.

Field consequence. Sham-link adjacency Down with MPLS core healthy? Do not begin with OSPF Hello timers. First verify each endpoint /32 exists in the correct VRF via BGP VPN reachability and is not accidentally originated into OSPF. If the sham link is Up but traffic takes the backdoor, compare two intra-area costs. If loops appear, inspect DN/VPN-tag behavior rather than simply lowering the sham-link metric.

MEMORY ANCHOR: Sham link fixes route-type preference; DN bit/VPN tag fixes route feedback. Cost cannot solve the wrong route type, and route type cannot solve a loop.

Scenario learning — new failure boundaries

A. Centralized RR gives the wrong exit only to one PoP

Symptoms: iBGP/RR sessions are Established; both egress paths exist at the RR; PoP-East should exit east but receives the west path favored by the vRR's own IGP cost. Evidence order: confirm equal higher-priority BGP attributes → verify both candidate paths at RR → inspect ORR client group/root → validate IGP link-state/rSPF eligibility → validate next-hop resolution table. Common mistake: raising LOCAL_PREF on the east path globally, which may break west clients. Correction: fix client/root ORR assignment or route-resolution eligibility. Memory anchor: wrong viewpoint, not necessarily wrong policy.

B. PAN-OS shows a dampening profile but flapping routes never suppress

Symptoms: profile exists after routing-engine migration; peer is Up; repeated updates continue. Check: engine type and PAN-OS release → migrated profile values → peer-group attachment → operational suppression/penalty state. If the firewall was on Advanced Routing PAN-OS 11.2.0, the documented issue could preserve configuration without applying it. Memory anchor: configured object ≠ enforced behavior.

C. EVPN fabric suddenly floods ARP after a scale change

Symptoms: Type-2 MAC routes remain; ARP broadcast counters rise. Check: MAC+IP binding population and limits → whether remote Type-2 includes IP → local snooping → anycast-gateway requirement on NX-OS → fabric-wide suppress setting → cache misses/silent hosts. Memory anchor: suppression fails open to flooding when it cannot safely answer.

D. Dense Wi-Fi 6 floor has unique colors but airtime remains saturated

Symptoms: colors are distinct; utilization/retries remain high. Check: client HE capability → OBSS RSSI relative to OBSS-PD threshold → AP/client spatial-reuse support → transmit power → channel plan. A different color does not let a station talk over a strong neighbor safely. Memory anchor: color is classification, not permission.

E. MPLS VPN is healthy but sham link never reaches Full

Symptoms: PE core LDP/BGP is healthy; CE routes exist; sham adjacency Down. Check before Hellos: local/remote sham endpoint /32s in correct VRFs and learned through BGP VPN reachability; ensure endpoints are not being advertised by OSPF; then verify sham-link config/area/authentication/metric. Memory anchor: sham OSPF adjacency depends on BGP VPN endpoint reachability.

Protocol-interaction map

  • ORR + Add-Path: ORR can only choose among candidate paths it actually knows; multi-RR designs may need Add-Path to preserve those candidates.
  • ORR + MPLS resolution: a VPN next hop resolved through LDP/RSVP can bypass Junos ORR's IGP-cost model unless resolution is intentionally changed.
  • Dampening + BFD: BFD can cause rapid route/session changes, while route damping intentionally hides repeated instability; diagnose liveness detection and advertisement suppression as separate clocks.
  • EVPN mobility + ARP suppression: a moved MAC changes which MAC-IP binding is authoritative; stale proxy state can continue answering after control-plane location changed.
  • BSS color + RSSI/SNR: color creates inter-BSS classification, while measured neighbor strength determines whether OBSS-PD spatial reuse is safe.
  • Sham link + BGP VPN: OSPF sham adjacency depends on BGP carrying endpoint /32 reachability; a BGP/MPLS failure can therefore present as an OSPF interface failure.
  • Sham link + DN bit: sham cost chooses between two intra-area paths; DN/VPN tag prevents feedback. Never use one as a substitute for the other.
