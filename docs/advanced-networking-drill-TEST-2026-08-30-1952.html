1. BFD implementation across vendors

BFD is a protocol-independent liveliness detector. It does not calculate a replacement path; the registered protocol consumes the Down event and convergence continues through protocol calculation, recursive next-hop resolution, RIB/FIB/LFIB programming and hardware forwarding.

Palo Alto Networks PAN-OS

PAN-OS supports BFD for BGP IPv4/IPv6 including single-hop and multihop, OSPFv2/OSPFv3, RIP and static routes. It uses asynchronous BFD. PAN-OS does not support BFD authentication, Demand mode, Echo mode, Poll sequences, congestion control or micro-BFD for LAG. On an OSPF broadcast network PAN-OS forms BFD sessions with the DR and BDR; point-to-point uses the direct neighbor and point-to-multipoint can use individual peers. Multiple routing clients using the same source/destination endpoints can share one BFD session. If the clients reference different BFD profiles, the effective session can be driven by the profile with the lowest Desired Minimum Transmit Interval. This means an aggressive timer chosen for one routing protocol can affect another protocol sharing that same BFD session.

A BFD failure for a static route can remove that route from the routing/forwarding tables. For BGP or OSPF the BFD event is delivered to the routing protocol, which then performs its own convergence logic. Therefore “BFD detected the fault in 300 ms” does not mean traffic was restored in exactly 300 ms.

Cisco IOS XE / IOS XR

Cisco exposes BFD both as a session and as a client-registration relationship. Useful verification includes show bfd interface, show bfd neighbors and client-specific forms such as show bfd neighbors client bgp ipv4. OSPF/OSPFv3, EIGRP, IS-IS and BGP can register with BFD depending on platform and release. Cisco documentation for OSPFv3 notes that BFD initiation is associated with an OSPF neighbor reaching FULL. EIGRP named mode can enable BFD at the address-family interface level.

A recurring Cisco field problem is mixing single-hop and multihop BFD. A loopback-sourced multihop BGP peer using BFD is not the same session model as directly connected interface BFD. Basic IP reachability can be healthy while the BFD/BGP relationship remains Down because the peers disagree about the BFD session type.

show bfd interface
show bfd neighbors
show bfd neighbors client bgp ipv4
show ip ospf neighbor
show ip ospf interface
show ip eigrp interfaces detail

Juniper Junos

Junos supports BFD across routing and service applications and also documents BFD over pseudowire VCCV and micro-BFD for LAG on supported platforms. The important design point is that “supports BFD” is not enough for interoperability. A design should identify the exact application, single-hop/multihop mode, address family, timer limits, multiplier, hardware/offload model and interaction with HA or graceful-restart functions.

Scenario

After configuring 100 ms BFD, OSPF and BGP flap while the interface remains Up. Verify negotiated Tx/Rx timers and multiplier, drops/load, client registration, and session type. On PAN-OS determine which shared profile is effective. On Cisco confirm the intended routing client registered the session and that single-hop/multihop behavior matches. The correction may be less aggressive timers or a session-model fix rather than changing BGP hold time.

2. EVPN/VXLAN fast convergence

A VTEP loopback ping proves underlay reachability, not tenant-service health. EVPN control-plane routes, VNI membership, FDB/MAC programming, ARP/ND, IRB/anycast gateway state and BUM handling are separate operational layers.

Arista EOS

EOS provides bfd vtep evpn interval <ms> min-rx <ms> multiplier <n> under the VXLAN Tunnel Interface. Arista ties this VTEP BFD function to BGP PIC Edge for EVPN/VXLAN remote-VTEP routes. Current documentation shows interval/min-rx values from 50 to 60000 ms and multiplier 3 to 50. A 100 ms interval with multiplier 3 gives a nominal 300 ms detection example. If VTEP BFD is Up while a host is unreachable, inspect the EVPN route, VNI/FDB state and endpoint programming rather than blaming liveness.

interface Vxlan1
   bfd vtep evpn interval 100 min-rx 100 multiplier 3

Cisco and Juniper comparison

Cisco and Juniper also separate underlay, BGP EVPN control-plane and VXLAN forwarding state, but the exact BFD/PIC attachment point varies by product and release. Do not translate Arista syntax literally. Compare capabilities: what protects the IGP, what protects the BGP session, what protects the VTEP, and what pre-installs backup forwarding.

Scenario

Remote VTEP loopback responds but remote host fails. Check underlay route, BFD/VTEP state, EVPN session, route type, route-target import/export, VNI membership, MAC/IP table, ARP/ND and FIB. A successful VTEP ping should move the fault boundary upward, not close the case.

3. Wireless: RSSI, SNR, utilization and roaming

RSSI measures received signal strength, not user throughput. SNR compares wanted signal to the noise floor. Co-channel interference is same-channel airtime contention; adjacent-channel interference is spectral overlap. Strong RSSI can coexist with poor performance when utilization, retries, noise or roam/authentication latency are high.

HPE Aruba Networking

Aruba Central exposes channel utilization separated into Tx, Rx and non-Wi-Fi interference, plus noise floor, retries, errors and drops in RF summaries. Roaming Experience provides source/destination AP, roaming type, band, RSSI and roaming latency; Aruba troubleshooting guidance flags roaming latency above roughly 50 ms as high in that workflow. ClientMatch monitors connected-client RF condition including RSSI and can identify sticky-client behavior. 802.11v-capable clients can receive transition suggestions. For non-802.11v clients Aruba can use more forceful steering methods that discourage association on selected radios and trigger reassociation. AirMatch/ARM optimizes channel and power; simply increasing AP power can create oversized/asymmetric cells and sticky clients.

Juniper Mist

Mist explicitly states that the client controls the roaming decision. It exposes roaming history and supports 802.11k/v/r. 802.11k supplies neighbor information to reduce scanning effort, 802.11v allows network-assisted transition suggestions, and 802.11r accelerates the security transition between APs. Throughput at a given RSSI can vary substantially, so a -58 dBm client can still perform badly if airtime/noise/retry conditions are poor.

Cisco RRM

Cisco RRM similarly considers interference, noise, traffic load and coverage measurements when optimizing RF channel/power choices. The product names differ, but the design objective is shared: control channel reuse, power, cell size and transition quality instead of treating RSSI as a single health score.

Scenario

Client RSSI is -58 dBm but throughput is 2 Mbps. Check SNR/noise floor, Tx/Rx/non-Wi-Fi utilization, retry rate, PHY/MCS, channel width, client band, roam history and authentication delay before increasing transmit power.

4. Pseudowire BFD over VCCV

VCCV provides OAM within a pseudowire service context. BFD over VCCV monitors that service-path liveliness, which is more specific than pinging PE loopbacks. PE reachability and LDP adjacency can remain healthy while a Layer-2 circuit service is broken.

Juniper Junos

Junos supports BFD for VCCV with LDP-based Layer-2 circuits, BGP-based L2VPNs and VPLS. Juniper documents distributed processing on supported forwarding hardware, which reduces Routing Engine load and improves session scalability. Applicable designs can require lo0 unit 0 family mpls; ACX platforms can require control-word configuration on both pseudowire peers. Verification commonly includes show l2circuit connections and show bfd session.

show l2circuit connections
show bfd session
show route table mpls.0
show ldp session

Scenario

PE loopbacks ping and LDP is established, but pseudowire is Down. Check local/remote attachment circuit, control-word/VCCV capability, BFD session, transport LSP and label programming. Do not use successful IP ping as proof of Layer-2 service health.

RFC 5885 · Juniper BFD for VCCV

5. Layered troubleshooting workflow

Work from the first broken state boundary: Physical/Radio → Layer 2 → Layer 3 → IGP → BFD/OAM → BGP/MPLS/Overlay → Policy → FIB/LFIB/FDB/NVE → Application/Client. Verify the liveness detector separately from its routing/service client, and verify control-plane state separately from forwarding-plane programming.
