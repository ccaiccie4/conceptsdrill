Beginner primer

Route reflector (RR): an iBGP speaker allowed to re-advertise iBGP-learned routes. Cluster: an RR and its clients. Recursion: resolving a route's next hop through another route or tunnel. FEC: packets receiving the same MPLS forwarding treatment. MST region: switches sharing one MST configuration identity. CAPWAP: AP-controller tunneling. DTLS: datagram TLS used to authenticate and protect CAPWAP control exchange.

Did You Know #1 — RR loop prevention does not guarantee path completeness

Route reflectors deliberately violate the normal iBGP split-horizon rule, so RFC 4456 adds ORIGINATOR_ID and CLUSTER_LIST. ORIGINATOR_ID records the original iBGP speaker's router ID. CLUSTER_LIST records the cluster IDs of reflectors that have handled the route. A reflector that sees its own cluster ID in CLUSTER_LIST rejects the advertisement; the original speaker rejects a route whose ORIGINATOR_ID equals its own router ID.

Cisco: the default cluster ID is the BGP router ID unless explicitly configured. Redundant RRs serving one logical cluster should share a cluster ID so sibling-reflected routes are recognized as already traversing that cluster. Cisco's multiple-cluster-ID feature can associate cluster identities per neighbor. show ip bgp exposes originator and cluster-list state.

Juniper: Junos documents client→client, client→nonclient and hierarchical reflection rules. Junos also warns that adding/changing cluster configuration can reset related BGP sessions in some designs. A dual-role ASBR/RR may attach reflection attributes to EBGP-learned routes when sending them to RR clients.

Failure consequence: every BGP session can be Established while a client lacks an alternate path because classic RR best-path selection only reflects selected paths. Loop prevention and path diversity are separate problems.

Memory anchor: ORIGINATOR_ID asks “did this start with me?” CLUSTER_LIST asks “did this already cross my cluster?” Neither asks “did I receive every viable path?”

Did You Know #2 — BGP confederations are eBGP-like inside but one AS outside

A confederation splits one operational AS into member sub-ASes. On Cisco, bgp confederation identifier <AS> defines the external identity and bgp confederation peers <sub-AS> identifies member peers. Sessions between member sub-ASes behave eBGP-like in important operational ways, while the entire confederation presents a single AS to true external peers.

The hard part is policy semantics: confederation-specific path segments exist internally but are not exposed externally as ordinary internal AS history. A policy that matches path information inside the confederation can therefore see different structure from a policy at the external edge. Treat the confederation boundary as a semantic change point for next-hop, MED and AS-path-based decisions.

Memory anchor: inside = eBGP-like sub-AS boundaries; outside = one AS identity.
Recall: Which Cisco command defines the external confederation AS? Why can't an external peer reconstruct every internal member sub-AS?

Did You Know #3 — LDP–IGP synchronization prevents an IP-valid but label-unready path

IGP and LDP converge independently. After a link recovers, OSPF or IS-IS can prefer it before LDP has a usable session and label bindings. MPLS traffic can then follow a path that is perfectly valid for IP but not yet valid for label switching.

Junos: ldp-synchronization causes the IGP to advertise the affected link with maximum metric while LDP is not fully operational. The link remains in topology but is intentionally unattractive. Juniper documents support on active point-to-point interfaces and LAN interfaces configured as point-to-point under the IGP, and notes that synchronization is not supported during graceful restart. A hold time can preserve max metric long enough for large FEC/label databases to synchronize.

Recursive forwarding: Junos LDP installs MPLS tunnel next hops in inet.3; BGP commonly resolves next hops through inet.3 first. A BGP route can therefore be present while the actual MPLS forwarding dependency is not ready.

Memory anchor: the IGP answers “where is the egress?” LDP answers “what label reaches it?” Sync prevents the first answer from becoming preferred before the second exists.
Recall: Why max metric instead of interface shutdown? Which Junos table often provides MPLS recursion for BGP? What HA caveat does Juniper document?

Did You Know #4 — MST region identity has a hidden third component

MST region membership requires an identical name, revision, and VLAN-to-instance mapping. The full mapping is not carried in the BPDU; a digest derived from the mapping is carried. Two switches can display the same name and revision and still be in different regions because one VLAN maps differently.

Cisco: a digest mismatch makes the receiving port a region boundary. Arista EOS: show spanning-tree mst configuration digest exposes the digest; EOS documents default revision 0 and range 0–65535. HPE Aruba AOS-CX: the Web UI exposes region name, revision and mapping digest, making digest comparison a useful cross-vendor normalization point.

Memory anchor: MST region identity = name + revision + mapping digest. Matching two of three is still a boundary.
Recall: Why doesn't the BPDU carry the full map? What command on EOS exposes the digest? What does matching digest prove—and not prove?

Did You Know #5 — Catalyst 9800 Discovery success does not prove DTLS identity success

CAPWAP AP join is a state machine: Discovery → DTLS Setup → Join → Image → Configure → Run. CAPWAP control uses UDP 5246; data uses UDP 5247. A Discovery Response proves AP-controller reachability, but protected join traffic still depends on successful DTLS authentication.

Certificate edge: Catalyst 9800-CL lacks the appliance hardware SUDI/MIC identity and requires an appropriate self-signed/controller certificate. Cisco also documents an interoperability case where older APs with SHA1-signed MIC chains can fail DTLS against controllers using SHA2 SUDI chains. A temporary controller self-signed certificate can permit AP upgrade, after which the workaround should be removed.

Evidence-first checks: show wireless stats ap discovery proves discovery requests reached the WLC. show wireless stats ap join summary identifies the failing phase. show wireless dtls connections, show wireless management trustpoint, and show wireless certification config isolate DTLS/certificate/cipher state. AP-side debug capwap client events and debug dtls client error expose the transition failure.

Even Run does not prove client data forwarding: policy tags, WLAN/policy profile, VLAN reachability, DHCP, authentication and upstream switching remain separate domains.

Memory anchor: Discovery proves reachability; DTLS proves identity/trust; Join/Configure proves control provisioning; Run still does not prove client forwarding.
Recall: Which phase can fail on certificate trust after Discovery? What exactly does AP discovery statistics prove? Why is 9800-CL different?

Spaced repetition — new angle: 802.11r changes security transition, not roam ownership

The prior drill emphasized RSSI/SNR/utilization. Today the retention angle is key management. Juniper Mist exposes local PMKID caching, Opportunistic Key Caching (OKC), and standards-based 802.11r. Local PMKID caching does not share state across APs and therefore scales poorly for roaming; OKC is widely supported but non-standard; 802.11r standardizes faster key/authentication transition.

Enabling 802.11r does not force a sticky client to move at a chosen RSSI. The client still chooses when to roam; 11r reduces the security transition cost after that choice.

Memory anchor: 11k = neighbor knowledge; 11v = steering suggestion; 11r = faster security transition; client still decides when.
Juniper Mist — RSSI, Roaming, and Fast Roaming — fast-roaming modes and client-owned roaming.

Real-world scenarios

RR session Up, prefix missing

Check selected-path state, ORIGINATOR_ID/CLUSTER_LIST, client/nonclient role, and whether RR best-path selection hid the alternate. Do not reset transport merely because a route is absent.

Memory anchor: transport, route validity and path diversity are different questions.

MPLS VPN blackhole after IGP recovery

IGP is healthy and BGP route remains, but LDP labels are not ready on the newly preferred link. Check LDP session/bindings and inet.3 recursion; tune LDP–IGP synchronization rather than BGP timers.

Memory anchor: reachable egress ≠ labeled egress.

MST unexpected region boundary

Name and revision match. Compare mapping digest. One forgotten VLAN mapping is sufficient to create a different region.

Memory anchor: name + revision + digest.

9800 discovery works, join fails

Discovery counters increment but join summary stops at DTLS with bad-certificate logs. Verify trustpoint, certificate chain, DTLS connections, time validity and old-AP certificate compatibility. Lower-layer discovery is already proven.

Memory anchor: discovery proves reachability; DTLS proves identity.
