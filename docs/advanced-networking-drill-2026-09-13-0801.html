BGP next-hop tracking: reachability events and metric events do not deserve the same urgency

Why this is hard to recall. BGP best-path selection depends on the recursive reachability of NEXT_HOP, but modern implementations do not treat every next-hop change identically. A route can remain reachable while its IGP cost changes; another event can make the next hop completely unreachable. Those two events should not necessarily trigger the same amount of immediate churn.

Cisco IOS XR. Current Cisco 8000/NCS documentation classifies next-hop events into critical and noncritical. Reachability, connected/local state, and first-hop/interface changes are critical and are delivered immediately to BGP. Recursed IGP metric changes are noncritical and are batched; the current guide documents a three-second interval by default. nexthop trigger-delay can change batching by AF, while nexthop route-policy constrains which RIB routes are acceptable resolvers.

Cisco IOS XE. Next-Hop Address Tracking replaces reliance on the old periodic scanner model for reachability reaction. The documentation still explains the historical 60-second scanner and why event-driven RIB notifications improve convergence. A BGP route is usable only when its NEXT_HOP recursively resolves.

Juniper. Junos Evolved supports recursive resolution over BGP multipath on supported platforms: when the resolver route itself has several feasible paths, a protocol next hop can inherit all feasible resolver paths instead of a single one. That matters in BGP-underlay designs: “the resolver is one BGP prefix” does not necessarily mean “one immediate forwarding next hop.”

Arista EOS 4.36.2F. EOS exposes explicit next-hop resolution RIB profiles, including system-unicast and tunnel RIBs. Profiles are ordered: resolution stops at the first RIB domain that succeeds. A route-map can select different resolution domains per route; a route that receives no profile can remain unresolved. show rib next-hop ... detail exposes the chosen resolution domains and flags unresolved, recursive-loop, and ARP/ND failures.

MEMORY ANCHOR: BGP does not forward to NEXT_HOP directly—it forwards to whatever the resolver says NEXT_HOP means now. Reachability changes are existential; metric changes are optimization changes.

OSPF packet pacing: flood queues, retransmission queues, and periodic refresh groups are three different schedulers

Why this is hard to recall. Engineers frequently confuse OSPF LSA throttling, SPF throttling, and packet pacing. Throttling controls when an LSA is originated or when SPF runs. Packet pacing controls how already-existing LSAs are placed into update packets and transmitted.

Cisco IOS XE. Current documentation exposes separate flood pacing, retransmission pacing, and LSA-group pacing. Flood pacing spaces packets in the normal transmission queue. Retransmission pacing spaces packets in the retransmission queue. Group pacing batches periodic LSA refresh/checksum/aging work to improve packing density; it does not change the normal 30-minute refresh lifetime of an individual LSA. Current IOS XE guidance says these defaults fit most networks and should be changed only after summarization, area design, queue and buffer approaches are exhausted.

Concrete defaults. Cisco documents retransmission pacing at 66 ms by default, configurable from 5–200 ms. Group pacing is commonly 240 seconds, range 10–1800 seconds. Large LSDBs can benefit from a shorter group interval because more refresh work must be spread across time; tiny LSDBs can tolerate a longer interval.

Juniper. Junos offers a different but related control: flood-reduction sets DoNotAge on self-generated LSAs so unchanged LSAs do not need periodic 30-minute reflooding. Junos also supports lsa-refresh-interval; current documentation states a Juniper refresh default of 50 minutes and a range of 25–50 minutes for that knob, while MaxAge remains 60 minutes. If interface flood reduction is configured, it takes precedence for that interface.

Misdiagnosis. A neighbor retransmission queue growing does not imply SPF is slow. It may mean packet loss or retransmission pacing is deliberately limiting bursts. Conversely, changing SPF throttle cannot drain a transmit queue that is already populated.

MEMORY ANCHOR: Origination creates LSAs, SPF consumes topology, and pacing schedules packets. Same protocol, different queues and clocks.

TI-LFA versus microloop avoidance: local repair solves the first milliseconds; ordered convergence solves the next seconds

Why this is hard to recall. Fast reroute and microloop avoidance both mention “loop free,” but they protect different phases. TI-LFA is a local repair activated at the failure-adjacent node before global SPF convergence finishes. Microloop avoidance handles transient loops created because different routers install the new topology at different times.

Cisco Segment Routing. TI-LFA precomputes a post-failure segment list that can protect links, nodes, and SRLGs. Cisco's current IP Flexible Algorithm documentation makes a subtle dependency explicit: IP Flexible Algorithm cannot get TI-LFA or microloop avoidance by itself; the matching SR data plane must also be enabled for that algorithm and the same participating router set must be reachable.

Cisco SRv6. Current 2026 documentation describes microloop avoidance by constructing temporary SR policies/segment lists toward destinations that would otherwise be exposed to transient loops after SPF. These temporary paths are withdrawn after ordered convergence stabilizes.

Juniper. Junos microloop-avoidance post-convergence-path installs a temporary post-convergence path for destinations at risk. Current defaults retain the temporary path for 5000 ms; configurable delay is 500–60000 ms. Juniper explicitly says microloop avoidance is not a replacement for TI-LFA. The two features stack in time: immediate local repair, then loop-safe global convergence.

Failure consequence. A link can fail with zero immediate loss thanks to TI-LFA and still experience packet loss a second later if inconsistent SPF/FIB updates form a microloop. Conversely, enabling microloop avoidance without local FRR can still leave the initial detection/repair gap.

MEMORY ANCHOR: TI-LFA answers “what do I do immediately when my adjacent resource dies?” Microloop avoidance answers “how do all routers change their minds without temporarily pointing at each other?”

EVPN DF non-revertive election: recovery can be more disruptive than failure

Why this is hard to recall. DF election is usually discussed as a failure event. In large multihomed services, the recovery event can cause a second disruption: the original preferred PE returns, becomes DF again, and triggers service re-carving. Non-revertive election deliberately prevents that second churn.

Standards baseline. RFC 8584 extends EVPN DF election beyond the original modulus algorithm with HRW and AC-influenced candidate pruning. The candidate set can change when attachment-circuit state changes; DF election and “which PE should forward BUM toward the Ethernet Segment” are therefore service/Ethernet-Tag scoped.

Cisco IOS XR. Current 2026 Cisco 8000 documentation supports preference-based and access-driven methods. Preference-based election assigns weights; the highest preference wins. In port-active preference-based mode, non-revertive allows the backup DF to remain DF after the failed node/link recovers, avoiding immediate service re-carving. A revert timer can later restore revertive behavior. Current restrictions are important: non-revertive is not supported with access-driven DF election, vES/NVE/PWHE virtual interfaces, or SRv6 in the cited implementation.

Juniper. Junos preference-based DF election supports highest/least preference choices and a non-revertive option. The reason is operational stability: the recovered former DF does not automatically preempt the currently working DF. This can be valuable when hundreds or thousands of EVIs would otherwise re-carve.

Arista. I found current EOS EVPN documentation for route/next-hop behavior in this run but no equally explicit authoritative 4.36.2F non-revertive-DF implementation reference. This report therefore does not assign Cisco/Juniper-specific non-revertive CLI semantics to EOS.

MEMORY ANCHOR: Revertive design optimizes for preferred steady state. Non-revertive design optimizes for stability after recovery.

PAN-OS BFD negotiation: the fastest configured timer is not necessarily the negotiated timer

Why this is hard to recall. BFD is negotiated. Your Desired Min Tx is constrained by what the peer says it can receive; your Required Min Rx constrains what the peer may transmit. The detection multiplier used for failure detection comes from the remote peer. Reading only the local profile can therefore give the wrong failure-time expectation.

PAN-OS timer floors. Current PAN documentation gives platform-dependent minimums. PA-7000/PA-5450/5430/5420/5410/3400 can use 50 ms; PA-3200 minimum is 100 ms; PA-400 minimum is 150 ms; VM-Series minimum is 200 ms. Default Tx/Rx interval is 1000 ms and default multiplier is 3. Aggressive values appropriate to a router ASIC may be a poor choice on a session-based firewall under dataplane load.

Negotiation rule. For a peer's sending direction, the effective transmit interval is constrained by the sender's Desired Min Tx and receiver's Required Min Rx—the larger requirement wins. PAN operational output exposes Received Min Rx, Negotiated Transmit Interval, Received Multiplier, Detect Time, and diagnostic code. Those fields are stronger evidence than the configured profile alone.

Hold Time. PAN BFD Hold Time is a start delay for Active mode after link-up. During the hold time the firewall does not transmit BFD, and received BFD control packets are ignored. That can create a confusing period where the physical link is Up but BFD intentionally has not started validating the path.

Multihop BFD. PAN supports multihop BFD for BGP. Minimum Rx TTL drops received BFD packets whose TTL is smaller than configured. That is a source-distance guard analogous in spirit to GTSM. It is not the BFD detection multiplier and does not determine session failure time.

MEMORY ANCHOR: BFD timing is bilateral: I say how fast I want to send, you say how fast you can receive, and the slower constraint wins. Failure time uses the peer's multiplier.

802.11v BSS Max Idle Protected: a keepalive can arrive and still not reset the idle timer

Why this is hard to recall. BSS Max Idle lets the AP tell the client how long it may remain silent before disassociation. Protected mode adds a security condition: only an authenticated/RSN-protected frame can reset the timer. So “the client sent something” is not enough; the frame must satisfy the protection requirement.

Cisco Catalyst 9800. Current IOS XE 26.1 documentation advertises the idle value in association/reassociation response frames. BSS Max Idle Protected tells the AP to accept only authenticated frames encrypted with RSN information to reset the idle counter. Without protected mode, any client data or management frame—encrypted or not—can reset it. The feature lives alongside BSS Transition Management and Directed Multicast Service (DMS), but these are different 802.11v functions.

Why this matters for battery. Before a client knows the AP's idle limit, drivers may send conservative keepalives to avoid unexpected disassociation. Advertising Max Idle allows longer sleep. DMS solves a different battery problem by converting requested multicast delivery to unicast so capable clients need not wake at every DTIM for those streams.

Apple client behavior. Apple documents support for BSS Transition Management, Disassociation Imminent, DMS, and BSS Max Idle on supported iOS/iPadOS/macOS devices. This is useful client-side confirmation that the IE can materially change enterprise client behavior.

HPE Aruba contrast. Aruba's roaming guidance centers on 802.11v BSS Transition Management/ClientMatch. In this run I did not find an authoritative Aruba reference exposing the same BSS Max Idle Protected control, so this report does not assume it exists. Aruba does document that a capable client can reject a BSS Transition request and the AP honors that result in the cited roaming design—another reminder that 802.11v contains multiple independent services.

MEMORY ANCHOR: Max Idle tells the client “how long may I sleep?” Protected Max Idle adds “only a cryptographically valid frame proves you are still here.”

Scenario learning

1. BGP CPU spikes every time IGP costs oscillate, but reachability never drops

Separate noncritical metric events from critical reachability events. On IOS XR inspect next-hop event counters/timestamps, trigger-delay, route-policy, and resolver first-hop/interface changes. On EOS verify the resolution RIB profile and show rib next-hop. The correction may be event batching/policy—not increasing BGP hold timers.

2. OSPF retransmission queues grow although SPF is fast

Check loss/acknowledgment behavior and retransmission pacing before touching SPF throttle. Flood pacing governs normal transmission; retransmission pacing governs resend bursts; group pacing governs periodic refresh packing. Changing the wrong scheduler can make CPU worse without draining the problem queue.

3. TI-LFA saves the first packets, then a transient loop appears

Validate the local repair segment list, then inspect microloop-avoidance temporary paths and delay timers on routers along the post-convergence path. The root cause can be correct SPF results installed at different times.

4. EVPN survives a failure but loses traffic when the original DF comes back

That is recovery churn. Check preference-based service carving, current DF weights, non-revertive state, number of services to re-carve, and revert timer. Schedule intentional reversion rather than assuming “preferred node recovered” means “change roles immediately.”

5. PAN BFD profile says 50 ms, operational output says 200 ms

Read Received Min Rx and Negotiated Transmit Interval. The peer may require 200 ms. Then read Received Multiplier for Detect Time. If multihop, verify Minimum Rx TTL separately—it can drop otherwise valid BFD control traffic without changing timer negotiation.

6. Sleeping client sends a frame but is still disassociated for idle

If BSS Max Idle Protected is set, capture whether the frame was RSN-protected. Inspect association response IE, protected-keepalive bit, client RSN state, and timer. “Frame seen over the air” does not prove “frame qualified to reset idle.”

Protocol interactions

  • BGP + IGP recursion: BGP may stay Established while a RIB event invalidates thousands of prefixes sharing one next hop.
  • OSPF + packet loss: retransmission pacing controls recovery traffic after an LSA was not acknowledged; SPF throttle is downstream computation.
  • TI-LFA + microloop avoidance: immediate local FRR and ordered global convergence solve different time slices of one failure.
  • EVPN DF + service carving: a recovered PE can cause avoidable churn if the design is automatically revertive.
  • BFD + BGP multihop: negotiated timers detect path failure; Minimum Rx TTL can reject control packets for source-distance reasons.
  • 802.11v + RSN: Max Idle is power management; Protected Max Idle makes security state part of the liveness proof.
