Beginner primer

MED: an optional non-transitive BGP hint; lower is preferred only when paths are eligible for MED comparison. ELI/EL: MPLS labels identifying a flow-hash value. Overlay Index: an EVPN-space next hop requiring recursive resolution. Root Guard: blocks an unexpected superior root claim. Loop Guard: prevents a root/alternate port from forwarding when expected BPDUs disappear. RNR: Reduced Neighbor Report describing 6-GHz BSSs through another band. PSC: Preferred Scanning Channels, a reduced active-scan set in 6 GHz.

Did You Know That?

1. BGP MED — deterministic comparison and global comparison are different knobs

Standards/mental model. MED is usually compared only when candidate paths came from the same neighboring AS. That creates a subtle path-order issue: if candidates from different ASes are interleaved, the sequence of pairwise comparisons can affect which same-AS routes ever get compared on MED.

Cisco. Cisco's support article updated July 30, 2026 demonstrates that bgp deterministic-med removes this temporal dependency by grouping paths from the same neighboring AS before choosing the lowest-MED representative. bgp always-compare-med changes something else: it expands MED comparison to paths from different neighboring ASes. Cisco currently recommends always-compare-MED for new deployments, but consistency across the AS is critical because mixed best-path behavior can create unexpected routing.

Palo Alto Networks. PAN-OS exposes Always Compare MED and Deterministic MED Comparison separately. In the Advanced Routing Engine documentation, Always Compare MED defaults disabled while Deterministic MED Comparison defaults enabled. This is a useful interoperability trap: a PAN firewall can be deterministic without comparing MED across AS boundaries.

Juniper. Junos normally uses deterministic behavior; path-selection cisco-nondeterministic can intentionally reproduce nondeterministic behavior for interoperability. path-selection always-compare-med expands scope, while med-plus-igp adds IGP cost to the MED before comparison. Therefore the numeric MED displayed in BGP is not always the whole effective decision input.

Field consequence. If MED 10 loses to MED 20, first ask whether the two paths are MED-comparable. Then inspect deterministic/global-MED knobs and higher-priority attributes (LOCAL_PREF, AS_PATH, ORIGIN) before calling the result wrong.

MEMORY ANCHOR: deterministic-MED fixes order inside normal MED scope; always-compare-MED expands the scope.
Active recall: Which knob changes arrival-order sensitivity? Which knob compares different neighboring ASes? Why can the numerically lowest MED still lose?

2. MPLS Entropy Labels — ELI says the next label is safe to hash

Protocol baseline. Transit LSRs often see only an MPLS stack, not the original transport five-tuple. Hashing an arbitrary service label is a poor substitute because a forwarding label is not a flow identifier. RFC 6790 assigns Entropy Label Indicator label value 7. The label immediately below ELI is an Entropy Label derived by the ingress from packet flow fields.

The ingress LER has the packet context needed to hash source/destination/ports and derives an EL. Where capability is signaled, it pushes a stack including tunnel-label / ELI=7 / EL. Transit devices can use the EL for ECMP/LAG hashing without deep packet inspection. The EL is not a globally distributed FEC; it is a flow hash value in the ordinary 20-bit label space.

Cisco IOS XR. NCS 5500/5700 documentation describes BGP labeled-unicast entropy labels beginning in the 7.5.1 feature history, with specific platform/native-mode restrictions. The egress advertises Entropy Label Capability and the ingress pushes ELI/EL. Cisco explicitly limits the cited implementation to BGP labeled-unicast.

Juniper. Junos documents a hard-to-recall stitching-point issue: RSVP/LDP entropy may disappear with penultimate-hop popping before an inter-area/inter-AS BGP-LU stitching point. BGP-LU entropy-label insertion restores a hash input at that boundary. Junos can suppress entropy capability with policy and documents feature-specific IPv6 restrictions.

Arista EOS. EOS 4.25.2F introduced LDP entropy-label support tied directly to RFC 6790, specifically to avoid deep inspection and improve labeled ECMP distribution.

Field consequence. A network may be fully reachable yet badly polarized over ECMP. Check ELC signaling, the imposed label stack, ELI=7 placement, PHP/stitching behavior and hardware hash inputs before changing IGP/BGP metrics.

MEMORY ANCHOR: ELI says “the next label is hash data, not a forwarding instruction.”
Active recall: Why is ELI required? Why does ingress create EL? How can PHP remove useful entropy before a stitching point?

3. EVPN Type-5 Overlay Index — a prefix route can recursively depend on another EVPN route

Protocol baseline. RFC 9136 permits an IP Prefix (Type-5) route to carry an Overlay Index: an overlay-space next hop that can be a gateway IP, MAC or ESI. The ingress NVE recursively resolves that object to an egress PE/NVE. This is a second recursion chain above the IP underlay.

If recursive overlay resolution is used, the Type-5 MPLS label is normally zero. If a received route has label zero but no valid Overlay Index, RFC 9136 says to treat it as withdrawn. The Gateway IP is not part of the Type-5 route key, so gateway ownership can move while large numbers of prefix routes stay unchanged.

Arista EOS. Arista's Gateway-IP Overlay Index feature uses the Type-5 Gateway-IP field and resolves it against the target IP of a Type-2 MAC/IP route. The public TOI was updated January 30, 2026 and documents support starting in EOS 4.29.0F, with later enhancements. Arista also notes that not every RFC 9136 Overlay-Index type is supported in this implementation.

Juniper. Junos supports both pure Type-5 (direct next-hop plus Router-MAC) and standard Type-5 with Gateway-IP overlay next hop and supporting Type-2. Platform support differs significantly. Some QFX platforms support only pure Type-5; EX9200 supports gateway-address mode in documented combinations. On some QFX platforms enabling overlay-ecmp can restart the PFE, so a next-hop optimization can itself be operationally disruptive.

Field consequence. A Type-5 can remain best and a VTEP loopback can ping while the prefix blackholes because the Gateway-IP resolver Type-2 disappeared. Check Type-5 → overlay index → Type-2/ES → egress VTEP → underlay → VNI/VRF → FIB.

MEMORY ANCHOR: Type-5 can name the destination while another EVPN route answers “which NVE owns the next hop?”
Active recall: What does label zero imply? What route resolves Arista Gateway-IP mode? Why can thousands of Type-5 prefixes stay unchanged during gateway movement?

4. STP Loop Guard versus Root Guard — missing BPDUs and superior BPDUs are opposite failures

Root Guard. Root guard is a topology-policy mechanism: a port that should never point toward the root receives a superior BPDU. The port is placed into an inconsistent/blocking condition instead of allowing the downstream device to win root election.

Loop Guard. Loop guard protects a different condition. A root/alternate port is blocked because it is continuously receiving BPDUs that prove another path is better. If a unidirectional fault stops those inbound BPDUs while physical carrier remains Up, ordinary STP aging could eventually let the port become designated and forward, forming a loop. Loop guard freezes the unsafe transition.

Cisco. Cisco documents loop guard for point-to-point STP links and explicitly says root guard and loop guard cannot both be enabled on the same interface. MST has additional boundary-port behavior: a boundary port blocked by loop guard can be blocked across all instances.

Arista EOS. EOS documents an especially useful port-channel corner case: BPDUs are transmitted using the first operational member. If that member becomes unidirectional, loop guard can block the entire channel even though other members still forward data. Channel creation/destruction also resets component STP state, so LACP state and STP control-plane state must be verified independently.

Field consequence. Root guard belongs where receiving a better root claim is forbidden. Loop guard belongs where continued BPDU reception is the liveness condition keeping a redundant path safely blocked. Neither replaces physical-layer diagnostics such as UDLD; loop guard detects the STP symptom, not necessarily the optical cause.

MEMORY ANCHOR: Root guard = “BPDU too good.” Loop guard = “the BPDUs that kept me blocked disappeared.”
Active recall: Which guard sees superior BPDUs? Which sees missing BPDUs? Why can a healthy LACP bundle still be loop-guard blocked?

5. 6-GHz discovery — RNR and PSC exist because brute-force scanning is too expensive

Why it is different. The 6-GHz band exposes far more 20-MHz channels than legacy bands. A client that passively dwelled on every channel would spend seconds scanning and waste battery/airtime. Wi-Fi 6E therefore relies on out-of-band Reduced Neighbor Report information and constrained in-band discovery.

Cisco Catalyst 9800. Cisco documents that 2.4/5-GHz probe responses can include RNR describing 6-GHz BSSs. Active 6-GHz discovery uses Preferred Scanning Channels: every fourth 20-MHz channel, spaced 80 MHz apart. Cisco lists 15 PSC channels: 5, 21, 37, 53, 69, 85, 101, 117, 133, 149, 165, 181, 197, 213 and 229. RNR can also point a client toward a non-PSC BSS, allowing selective discovery rather than blind scanning.

Other in-band mechanisms include FILS Discovery and unsolicited probe responses. The important troubleshooting point is that “the AP is beaconing in 6 GHz” is not the same as “this client will efficiently discover it.” Client regulatory domain, drivers, security requirements and discovery behavior all matter.

Aruba AP-635 field evidence. An independent Aruba AP-635 lab captured RNR in 2.4/5-GHz beacons pointing to 6-GHz channel 101. In that test, an iPad stopped rediscovering the 6-GHz-only SSID when 2.4/5-GHz radios were disabled even though dedicated analyzers still saw the 6-GHz BSS. After moving the AP from an older 8.10 build to 8.11, FILS Discovery frames appeared. This is field/community evidence, not an official HPE release guarantee, and is deliberately labeled as such.

Field consequence. Troubleshoot discovery as: client regulatory/driver capability → 2.4/5 RNR → PSC/non-PSC channel plan → FILS/UPR for 6-GHz-only operation → WPA3/security → association. A packet analyzer and a normal client do not necessarily use the same discovery strategy.

MEMORY ANCHOR: RNR tells a client where to look; PSC reduces how many places it must actively look.
Active recall: Why only 15 PSCs? How can RNR help with a non-PSC BSS? Why might an analyzer see a WLAN that the client UI does not?
